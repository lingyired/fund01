# fund01 升级插件 v1.6.1 后：右键退出 workaround 回退指南

> 适用对象：fund01 维护者
> 日期：2026-08-17
> 插件版本：tauri-plugin-multiline-menubar **v1.6.1**（已发布：github.com/lingyired/tauri-plugin-multiline-menubar/releases/tag/v1.6.1）
> 前置结论：**插件 v1.6.1 已修复右键菜单退出挂起（用户实测通过）**，fund01 的 workaround 可以安全撤下，恢复标准 `quit` id + `app.exit(0)` 退出链路。

---

## 一、背景回顾

### 1.1 fund01 当前的 workaround（基于插件 v1.6.0 的缺陷）

插件 v1.6.0 存在一个 macOS 缺陷：右键菜单弹出（`popUpMenuPositioningItem:`）的 modal tracking loop 会**消费掉本次点击的 `rightMouseUp`**，导致 NSStatusBarButton 外层 `trackMouse:untilMouseUp:` 卡死在 `NSEventTrackingRunLoopMode`（菜单关了 tracking 还活着）。此时菜单 action 里**同步** `app.exit(0)` 会与卡死的 tracking 无限竞争 → 100% CPU + 内存增长 + 退出挂起，直到手动点击 menubar 才恢复。

fund01 为此绕开插件保留 id，改用应用层兜底：

```rust
// menubar.rs — set_standard_menu（现在）
MenuItemDescriptor::Item {
    id: "quit-fund01".to_string(),   // ← 自定义 id，刻意不用插件的 "quit"/"quit2"
    text: "退出 fund01".to_string(),
    ...
},

// menubar.rs — on_menu_event（现在）
} else if item_id == "quit-fund01" {
    std::process::exit(0);            // ← 直接杀进程，不依赖 tao run loop
}
```

### 1.2 插件 v1.6.1 的修复内容（两个改动，缺一不可）

| 层 | 改动 | 效果 |
| --- | --- | --- |
| native（`multiline_menubar.mm`） | 右键菜单关闭后**补发 `rightMouseUp`** | 按钮外层 tracking 正常收尾，run loop 回到 default mode，不再卡死 |
| Rust（`desktop.rs`） | `quit`/`quit2` 改为**延迟 ~200ms 异步** `app.exit(0)` | 不在菜单 action（tracking loop 内）同步退出，等菜单 dismiss + tracking 收尾后再在主 run loop 干净退出 |

**行为变更**：`quit` / `quit2` 语义 = **异步退出**（约 200ms 延迟）。宿主不应假设菜单事件回调内 app 已同步退出。

### 步骤 1：菜单项 id 改回标准 `quit`

同时更新函数上方的警告注释（约 611-618 行）——原注释基于 v1.6.0 的同步退出缺陷，已过时：

```rust
/// ⚠️ 退出项使用插件保留 id `quit`：插件 v1.6.1 起对该 id 延迟 ~200ms 异步
/// `app.exit(0)`（native 侧会补发 rightMouseUp 让 trackMouse 收尾），不再挂起。
/// 宿主无需、也不要在自己的 on_menu_event 里再处理该 id（见 on_menu_event 注释）。
```

### 步骤 2：删除宿主侧的 `quit-fund01` 处理分支

`apps/tauri/src-tauri/src/menubar.rs` — `on_menu_event`（约 774-781 行）：

```rust
pub fn on_menu_event(app: &AppHandle, item_id: &str) {
    if item_id == "open-settings" {
        open_settings_window(app, None, None);
    }
    // quit 由插件处理（QUIT_ITEM_IDS），宿主不监听；勿在此处加 quit/quit2 分支，
    // 否则会与插件异步退出竞争（如直接 process::exit 会抢先杀进程，跳过插件清理）。
}
```

> **为什么宿主不能自己处理 `quit`**：插件和宿主各自注册了 Tauri 全局 `on_menu_event`，事件会**同时**送达两边。插件收到 `quit` 后负责延迟退出；宿主若在同一事件里 `process::exit(0)`，会抢先杀进程、跳过 tauri 正常退出清理。标准 id 就该交给插件。

同步更新 `on_menu_event` 函数上方的长注释（约 763-773 行，同样基于 v1.6.0 缺陷，可删除或改写为上面的简短说明）。

### 步骤 3：更新 lib.rs 的过时注释（可选，纯注释）

`apps/tauri/src-tauri/src/lib.rs:128`：

```rust
// 改前
// 显式退出（右键菜单「退出 fund01」→ 插件 app.exit(0)）code.is_some() → 放行。
// 改后
// 显式退出（右键菜单「退出 fund01」→ 插件 quit 延迟 app.exit(0)）code.is_some() → 放行。
```

**代码逻辑无需改动**：`ExitRequested { code: Some(0) }` → `code.is_some()` → 放行；`RunEvent::Exit` 日志照常。这条路径在改回标准 `quit` 后正是插件 `app.exit(0)` 触发，行为正确。

> `window.rs` 的 `install_terminate_hook`（Dock 右键退出 / Cmd+Q 改写为「只关窗口、menubar 常驻」）与右键菜单退出**无关**，不要动。

## 三、调整后的退出链路（期望行为）

```
右键「退出 fund01」→ muda action → Tauri 全局 on_menu_event
  ├─ 插件 handler：命中 QUIT_ITEM_IDS → 200ms 后 app.exit(0)
  │    （native 已补发 rightMouseUp → trackMouse 收尾 → run loop 回 default mode）
  └─ 宿主 handler：只处理 open-settings，quit 不匹配 → 无事发生
200ms 后 → app.exit(0) → ExitRequested { code: Some(0) } → 放行 → RunEvent::Exit → 进程干净退出
```

无 100% CPU、无内存增长、无「要手动点 menubar 才关」。

## 六、常见问题

**Q1：只升级插件版本、不改代码可以吗？**
可以。workaround 在 v1.6.1 下继续有效（`process::exit` 秒退），且还能白拿 native 层 tracking 修复。只是退出不走 tauri 清理流程、且代码里留着一套「已修复问题」的绕行逻辑。**建议**按本指南撤下 workaround，恢复标准路径。

**Q2：为什么 v1.6.1 里退出延迟了 200ms，会不会感觉变慢？**
不会。200ms 是菜单 dismiss + tracking 收尾的时间，宿主感知仍是「点完即退」。

**Q3：宿主以后还能用自定义退出 id 吗？**
可以，任何非 `quit`/`quit2` 的 id 插件都不拦截，宿主完全自管。只是既然标准 id 已可用，没必要再维护一套。

**Q4：如果插件 v1.6.1 之后仍有边缘场景挂起？**
fund01 的 `process::exit` 兜底始终有效，两者不冲突；可随时按第五节回滚。
