# 持仓截图 → 导入 JSON：AI Agent 提示词规则

用于让豆包/GPT 等助手把「基金 App 持仓截图」转成 fund01 扩展「导入持仓」能吃的 JSON。

## 背景：截图里有什么、缺什么

天天基金 / 支付宝 / 券商 App 的持仓页通常只有四个数：

| 截图字段 | 映射 | 作用 |
|---|---|---|
| 资产 / 持仓金额 | `amount` | **必填**，折算份额的唯一依据 |
| 昨日收益 / 今日收益 | `dailyProfit` | 不参与计算，**做口径校验** |
| 持仓收益 / 累计收益 | `holdProfit` | 反推成本 |
| 持仓收益率 | `holdProfitRate` | 反推/校验成本 |

**缺的是「持有份额」和「成本单价」。** 扩展内部只存份额，所以必须用
`份额 = amount ÷ 基准净值` 折算。

## ⚠️ 最关键的一件事：`amount` 对应的是哪一天的净值

`amount` 是市值，市值 = 份额 × 某一天的净值。**折算时必须用同一天的净值**，
否则份额会整体偏掉一整天的涨跌幅，而且**看不出来**（导入后显示的金额恰好等于你录入的数，
一切看起来都对，实际份额已经错了）。

判断依据就在截图上——**「今日收益已更新」字样**：

| 截图状态 | `amount` 锚定 | 填 |
|---|---|---|
| 显示「今日收益已更新 / 今日收益更新」 | 今日确认净值 | `"amountBasis": "today"` |
| 无该字样（盘中估算、尚未更新） | 上一交易日确认净值 | `"amountBasis": "prev"`（默认） |
| 截图能读到具体净值日期 | 该日期净值 | `"navDate": "2026-08-01"`（**最稳**，优先于 amountBasis） |

### 填错的代价有多大（真实数据）

025687 在 2026-08-03 当日净值 **-10.11%**：

| | 07-31 净值 | 08-03 净值 |
|---|---|---|
| | 1.9564 | 1.7586 |

假设截图 `amount = 27538.49`、实际是 07-31 收盘口径（今日收益未更新）：

- ✅ 填 `prev` → 份额 = 27538.49 ÷ 1.9564 = **14076.31**，展示 = 14076.31 × 1.7586 = 24754.6（正确反映今日 -10.11%）
- ❌ 填 `today` → 份额 = 27538.49 ÷ 1.7586 = **15659.10**，份额虚高 **11.2%**，且展示仍是 27538.49，今天这 -10% 凭空消失

反过来，若截图确实是「今日收益已更新」而误填 `prev`，份额会少 11.2%。
**波动越大的基金，填错代价越大。**

## `dailyProfit` 为什么建议填

它是没有份额时**唯一能自动纠错**的信号。扩展会用
`理论收益 = 份额 × (最新确认净值 − 前一日净值)` 反过来验你的 `amount`，
偏差超过 5% 就在导入结果里弹黄色提醒。能抓住「amount 填成本金」「拆分组时收益没拆」这类量级错误。

### ⚠️ 但收益栏显示 `0.00` 时，请**省略这个字段**，不要填 0

基金 App 在**非交易日空窗期**会把收益栏显示成 `0.00`，这表示「无数据」而不是「收益为零」：

- 周末 / 节假日（昨天压根没有净值）
- 周一今日净值尚未更新时，「昨日收益」字面指昨天（周日）= 0
- 当天新买入、份额尚未确认

而真实收益恰好是 `0.00`（净值四位小数完全不动）的概率极低。

**填 0 会导致必然误报**：相对偏差公式 `|理论值 − 0| ÷ max(|理论值|, 0)` 在 0 处恒等于 100%，
只要基金当天有涨跌就一定告警。真实案例（2026-08-03 周一，019924）：

```
录入 dailyProfit: 0  →  019924：昨日收益对不上（录入 0.00 元，应为 23.31 元，偏差 100.0%）
```

数据其实完全正确，纯属误报。

> v1.0.83 起扩展已把校验中的 `0` 一律按「无数据」处理并静默跳过，
> 所以**填了 0 也不会再误报**。但仍建议直接省略，语义更干净。
> 同理，`holdProfit: 0`（新买入当天）也不再触发成本交叉校验误报——
> 但它仍会正常用于推导成本（成本 = 市值）。

## Schema 文件与校验

完整版 Schema（每个字段带详细 `description`、`examples`）单独存在
[`docs/import-schema.json`](./import-schema.json)，可直接：

- 喂给支持 structured output / JSON mode 的模型作为 `response_format`
- 作为独立文件校验 agent 的输出

校验一份输出：

```bash
python3 -c "
import json,sys
from jsonschema import Draft202012Validator
s=json.load(open('docs/import-schema.json'))
d=json.load(open(sys.argv[1]))
errs=sorted(Draft202012Validator(s).iter_errors(d), key=lambda e: e.path)
print('OK') if not errs else [print(f'第{list(e.path)[0]+1 if e.path else \"?\"}项: {e.message}') for e in errs]
" output.json
```

> 已用 17 条用例验证过该 Schema：6 条正例通过，11 条反例（多余字段、code 写成数字、
> amount 带引号、amountBasis 拼错、shares 为 0、收益率漏 % 等）全部拦截。

### 用作 structured output 时的注意

各家 strict 模式对 JSON Schema 只支持子集，通常需要按其文档做这几步调整
（**这是给 API 调用方的，不影响扩展本身的解析**）：

- 把所有 `properties` 都列进 `required`，可选字段改用联合类型
  （如 `"type": ["number", "null"]`）表达"可为空"
- 去掉不受支持的关键字（常见不支持：`oneOf`、`minItems`、`exclusiveMinimum`、
  `default`、`examples`）——`holdProfitRate` 的 `oneOf` 可退化成 `"type": ["string","number"]`
- 保留 `additionalProperties: false`（strict 模式本就强制要求）

若模型不支持 structured output（如直接对话使用的豆包），直接整份粘贴
[`docs/import-prompt.md`](./import-prompt.md) 即可——它内部已嵌了同一份 Schema，效果基本等价。

### Schema 比解析器更严——这是有意的

Schema 是「给 agent 用的规范子集」，扩展的 `parseImport` 比它宽容。差异有三处，
都是**故意收紧**，不是 bug：

| 差异 | 解析器 | Schema | 收紧的理由 |
|---|---|---|---|
| `amountBasis` | 可省略，默认 `prev` | **required** | 逼 agent 显式表态。静默走默认值正是「份额偏一天」这类错误的温床 |
| 字段别名 | 认 `fundCode`/`money`/`basis`/`netValueDate`/`净值日期`/`costPrice`/`costBasis`/`totalProfit`/`cumProfit`/`share`/`份额`/`dayProfit`/`yesterdayProfit`/`profitRate`/`totalProfitRate`/`groups` | 只认规范名 | 输出唯一化；顺带把 `constantProfit`、`dailyProfitRate` 这类扩展根本不读的垃圾字段一并拦在门外 |
| `holdProfitRate` 字符串 | `"9.95"`（无 %）也认 | 必须带 `%` | 无 % 的纯数字串会走「|v| ≥ 1 视为百分数」的猜测分支，是歧义源 |

所以：**Schema 校验通过的一定能导入；校验没过的不一定不能导入**，但不该那么写。
（扩展 UI 里的占位示例 `IMPORT_SAMPLE` 就省略了 `amountBasis`，属解析器宽容范围，
不代表 agent 也可以省。）

## 字段优先级（扩展内部逻辑）

- **基准净值**：`navDate`（按日期精确匹配） > `amountBasis`
- **份额**：`shares` > `amount ÷ 基准净值`
- **成本单价**：`cost` > `(amount − holdProfit) ÷ 份额` > `holdProfitRate` 反推 holdProfit 后再算
- **`dailyProfit`**：永不参与计算，只做校验

## 基准净值的选取规则（v1.0.82）

设 `hist[0]` = 数据源最新确认净值，`hist[1]` = 再前一个交易日。

| 输入 | 选取 | 取不到时 |
|---|---|---|
| `navDate` = hist[0] 日期 | hist[0] | 报错并列出可用日期 |
| `navDate` = hist[1] 日期 | hist[1] | 同上 |
| `amountBasis: "today"` | hist[0]，且要求其日期 == 今天 | 报错（数据源今日净值未同步，稍后重试或改 prev） |
| `amountBasis: "prev"` | hist[0] 日期 == 今天 → 用 hist[1]；否则用 hist[0] | 报错 |

**关键：锚点是净值日期，不是 hist 下标。** hist 下标会随「数据源什么时候同步今日净值」漂移，
同一个 `prev` 在 18:00 和 22:00 该取的下标是不同的。

## 两条校验规则

| 校验 | 公式 | 触发阈值 | 说明 |
|---|---|---|---|
| 当日收益 | `份额 × (hist[0] − hist[1])` vs `dailyProfit` | 相对偏差 > 5% | 仅当基准锚定在 hist[0] 时执行；波动小于市值 0.05% 时跳过（净值 4 位小数舍入噪声） |
| 成本 | `holdProfit ÷ holdProfitRate` vs `amount − holdProfit` | 相对偏差 > 2% | 抓「数字不同源」 |

**跳过规则（v1.0.83）**：`dailyProfit` / `holdProfit` / `holdProfitRate` 中任意一个为 `0`，
对应的那条校验直接跳过——校验里的 `0` 一律按「无数据」处理。
因为相对偏差公式在 0 处恒等于 100%，把空窗期的 `0.00` 当真值必然误报，
而误报会让人对所有告警脱敏，代价远大于漏报。
注意：`holdProfit: 0` 只是不参与**校验**，它仍会正常用于**成本推导**（成本 = 市值 − 0）。

两条都**只告警不阻断**，导入照常完成，黄色提示框列出可疑条目。

## 代码 ↔ 名称交叉校验（v1.0.87）

AI 从截图识别基金代码时，常把一两位数字看错（如 009995「嘉实创新先锋混合C」被识成
009895「摩根瑞盛87个月定期开放债券」），而**基金名称往往识别正确**。错误代码通常也是一只
真实存在的基金，导入不报错，却装成了完全不相干的标的——极其隐蔽。

导入时（只要 JSON 带了 `name`）扩展会做交叉验证，三态：

| 状态 | 条件 | 行为 |
|---|---|---|
| 通过 | 传入 `name` 与**任一平台**官方名一致；或按 `name` 搜索到的候选里就含原代码（仅叫法差异） | 正常导入 |
| 自动纠正 | 名称不符，但按 `name` 搜索能**唯一**确定一只基金 | 改用正确代码重查并导入；结果顶部黄色提示「已按名称自动纠正」（exact=名称完全一致；loose=忽略「混合/股票」等类型词后一致） |
| **拒绝导入** | 名称不符，且按 `name` 搜索无法唯一确定 | **直接判失败、不写入任何数据**；导入结果里列为失败项，提示「代码与名称对不上，请核对代码是否识别错误」后重新导入 |

> 多个平台对基金叫法本就不同（如 fund123「嘉实低碳精选混合C」vs 天天基金「嘉实低碳精选混合发起式C」），
> 所以「官方名」同时采集 **fund123 searchFund 的 `fundInfo.fundName`** 与 **天天基金 FundMNFInfo 的 `SHORTNAME`**，
> 只要任一相符即视为代码正确，避免平台口径差异造成的误报。

实现要点（**宁缺毋滥，绝不擅自改数据**）：

- 名称校验在「拉板块 / 净值」**之前**完成；纠正后的代码会重新取元信息，不会混入错误基金的净值。
- 名称归一化：全角→半角、去括号与空格、英文大写；宽松匹配再剥离「混合/股票/债券/基金」等类型词，
  以兼容支付宝简称（如「嘉实创新先锋C」）。
- **末尾份额字母（A/C/E）绝不剥离**：009994=A、009995=C 是两只不同基金。
- 天天基金搜索接口是模糊匹配、**永远返回结果**（搜不存在的名字也返回 10 条无关基金），
  所以**绝不取第一条**，必须经名称精确过滤；宽松匹配还要求唯一命中且剥离后长度 ≥ 4，防误配。
- 解析结果 `name` 改为**官方名优先**（以前用户传入名优先，会掩盖「代码错、名字对」的错配）。

> 单只 / 自选手动添加表单不传 `name`，不触发本校验（人工手输代码，风险低）。
> 本校验只在「带 name 的导入」路径生效，与上面两条金额口径校验相互独立。

|---|---|
