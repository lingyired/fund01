## 1. 背景与目标

### 1.1 现状

桌面版（Tauri）当前只有「提示式更新」，实现于 `apps/tauri/src-tauri/src/update.rs`：

- 拉 `https://lingai.net/fund01/version.json`（自定义精简格式：`latestVersion` / `homepage` / `downloadUrl`）
- 比版本号 → 「关于」页 banner 提示「发现新版本 vX.Y.Z」+「下载新版本」按钮
- 按钮用 `open_external` 打开浏览器 → **用户手动下载 dmg/exe、手动替换**

缺口：整个安装过程全靠用户手动。对一个 menubar 常驻小工具，用户多半不会主动去换新版本。

### 1.2 目标

1. 应用内一键检查 → 下载 → 验签 → 安装 → 重启，**macOS 与 Windows 双端一致**
2. 安装包必须经签名验证，防止被篡改（现状完全没有校验）
3. 适应国内网络：GitHub Release 需可配镜像源，且镜像失效时不阻断主流程
4. 保留现有「关于」页 UI 位置与交互心智（发现新版本 → 一键更新）

### 1.3 非目标

- 不做静默后台自动下载安装（用户必须主动点击）
- 不做 delta / 差分更新（Tauri 官方不支持）
- 不做 Windows 便携版（portable）自动更新—— 见 §7 已知边界
- Chrome 扩展端不涉及（Chrome 扩展走应用商店自动更新）

## 2. 方案选型

### 2.1 为什么不用 Sparkle

**Sparkle 不支持 Windows。** 它是 macOS 原生框架，深度依赖 AppKit / LaunchServices / XPC，Windows 上无任何官方实现。

Windows 上的对应物是**独立项目 WinSparkle**（`vslavik/winsparkle`，仍活跃，0.9.3 / 2026-07 支持 VS2026），它与 Sparkle 共享 appcast 格式但**是完全独立的 C DLL**。接入 Tauri 需要：

- 手写 FFI 绑定（WinSparkle C API）
- 维护两套 appcast 清单、两套签名工具链
- 两端行为难以对齐

**结论：放弃。**

### 2.2 采用 `tauri-plugin-updater`

Tauri 官方插件，单套代码覆盖 macOS / Windows / Linux。关键特性：

| 特性 | 说明 |
|---|---|
| 签名校验 | **强制、不可关闭**。ed25519（minisign 格式）私钥签 `.sig`，公钥内置在 app |
| 端点 fallback | `endpoints` 为数组，**仅当返回非 2xx 才尝试下一个** |
| Windows 安装 | NSIS/MSI，`installMode` 控制静默程度 |
| 产物形态 | macOS `.app.tar.gz` + `.sig`；Windows `myapp-setup.exe` + `.sig`（v2 模式） |

**版本要求**：updater 插件需要 Rust ≥ 1.90（当前项目 `rust-version = "1.77"`，CI 用 `dtolnay/rust-toolchain@stable`，无需改 rust-version 声明但本地 toolchain 需确认）。

### 2.3 三路线对比

| 维度 | A · tauri-plugin-updater | B · 维持现状 | C · Sparkle+WinSparkle |
|---|---|---|---|
| 应用内安装 | ✅ | ❌ 浏览器手装 | ✅ |
| 包完整性校验 | ✅ 强制验签 | ❌ 无 | ✅ |
| 双端一套代码 | ✅ | ✅ | ❌ 两套 |
| 改造成本 | 中 | 零 | 高（FFI + 双清单） |
| macOS 需公证 | 是（否则体验差） | 是（现状已需 `xattr -rd`） | 是 |

## 3. 前置条件（阻塞项）

### 3.1 macOS Developer ID + 公证（必须）

**现状问题**：CI 用自签名证书 `Fund01`（`MACOS_CERT_P12` secret），本机 `signingIdentity: "-"`（ad-hoc）。用户装 dmg 报「已损坏」需手动 `xattr -rd com.apple.quarantine` —— 这正是**缺公证**的典型症状。

应用内更新会**替换 `/Applications/Fund01.app`**，替换后新 app 的签名/公证状态直接决定用户是否再遇到「已损坏」。自签名证书无法通过 Gatekeeper 的在线 notarization 校验。

**需要做的**：

1. Apple Developer Program 账号（用户已注册）→ 创建 **Developer ID Application** 证书（不是 Development）
2. 创建 **Developer ID Installer** 证书（公证 dmg 需要；仅更新 `.app` 可暂不需要，视公证提交对象而定）
3. 在 App Store Connect 创建 **API Key**（推荐，密钥不随密码轮换失效）或 App 专用密码
4. GitHub Secrets 替换：

| Secret | 现状 | 改为 |
|---|---|---|
| `MACOS_CERT_P12` | 自签 Fund01 | **Developer ID Application p12**（base64） |
| `MACOS_CERT_PASSWORD` | 有 | 同左 |
| `APPLE_ID` / `APPLE_PASSWORD` / `APPLE_TEAM_ID` | 无 | **新增**（公证） |
| `APPLE_API_KEY` / `APPLE_API_KEY_PATH` / `APPLE_API_ISSUER` | 无 | **新增**（API Key 方式，二选一） |
| `TAURI_SIGNING_PRIVATE_KEY` | 无 | **新增**（updater 签名私钥） |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 无 | **新增**（若私钥设密码） |

5. `tauri.conf.json` 的 `macOS.signingIdentity` 从 `"-"` 改为 `"Developer ID Application: <name> (<TEAMID>)"`，或统一由 CI 的 `APPLE_SIGNING_IDENTITY` env 覆盖（本机开发仍可保留 `-`）

> ⚠️ **同一版本号只能有一种签名来源**（现有约定）。切换到 Developer ID 后，本机 ad-hoc 产物与 CI 公证产物不可混用同一版本号。开发迭代本机包仍不进 Release。

### 3.2 Windows 无阻塞项

NSIS 安装器直接静默安装，不需要代码签名证书（SmartScreen 会警告，但现状已如此，不算新增退化）。

## 4. 架构

### 4.1 数据流

```
┌─ CI (tag push) ────────────────────────────────────┐
│  macOS job:  Developer ID 签名 + 公证 + stapling      │
│             → .app.tar.gz + .app.tar.gz.sig          │
│  Windows job: NSIS 安装器                            │
│             → Fund01_x.y.z_x64-setup.exe + .sig      │
└───────────────────────┬───────────────────────────────┘
                        │ 上传
                        ▼
            GitHub Release 资产（含 latest.json）
                        │
                        │ 客户端 endpoints 数组按序尝试
                        ▼
   ┌────────────────────────────────────────────┐
   │ ① https://lingai.net/fund01/updater/...    │  首选：自有源，可控
   │ ② https://gh-proxy.com/...latest.json       │  兜底：GitHub 代理
   │ ③ https://github.com/.../latest.json        │  最后：GitHub 直连
   └────────────────────┬───────────────────────┘
                        ▼
        tauri-plugin-updater：验签 → 下载 → 安装
                        ▼
              重启（tauri-plugin-process relaunch）
```

### 4.2 清单（latest.json）格式

**静态 JSON**（对应多平台，`platforms` 键为 `OS-ARCH`）：

```json
{
  "version": "1.7.0",
  "notes": "支持应用内自动更新",
  "pub_date": "2026-10-11T13:00:00Z",
  "platforms": {
    "darwin-aarch64": { "signature": "...", "url": "https://.../Fund01_1.7.0_aarch64.app.tar.gz" },
    "darwin-x86_64": { "signature": "...", "url": "https://.../Fund01_1.7.0_x86_64.app.tar.gz" },
    "windows-x86_64": { "signature": "...", "url": "https://.../Fund01_1.7.0_x64-setup.exe" }
  }
}
```

> ⚠️ **官方明确警告**：Tauri 在检查 `version` 字段**之前**会校验整个文件，所有 `platforms` 条目必须有效完整。某平台构建失败（Windows arm64 目前是 `experimental`）就**不能写进清单**——否则整个更新检查对所有用户失败。
>
> **决策**：清单由 CI 动态生成，**只收录本次成功构建的平台**。这样 Windows arm64 构建失败时，x64 用户的更新不受影响。

### 4.3 镜像策略

**依据 `tauri-plugin-updater-2.10.1` 源码实测**（`src/updater.rs:412-519` 的 endpoint 循环），行为比官方文档描述的更细致：

| 失败类型 | 代码路径 | 是否 fallback 下一个 endpoint |
|---|---|---|
| 被墙 / DNS 失败 / TCP 超时 / TLS 失败 | `Err(err)` → `last_error = Some(err)` | ✅ **会** |
| HTTP 非 2xx（如 GitHub 403/404） | `Ok(res)` 但 `!is_success()` → 仅 `log::error!` | ✅ **会** |
| HTTP 200 + JSON 解析失败 | 第 490 行 `res.json().await?` | ❌ **不会**，直接 `?` 跳出函数 |
| HTTP 200 + 签名验证失败 | 在下载后的 install 阶段 | ❌ 不会（且合理） |
| HTTP 204 No Content | 视为「无更新」立即返回 | 终止（符合语义） |

`last_error` 在每次成功解析时置 `None`（第 498 行），循环结束后统一抛出（第 523 行），语义干净。

**结论：「GitHub 被墙 → 自动退镜像」成立。** 但有两个例外必须处理（见下）。

#### endpoint 排列

清单直接挂 **GitHub Release 资产**（`releases/latest/download/latest.json`，Tauri 官方推荐），
无需自建部署 —— 项目本就人工 `gh release create`，发布时把 `latest.json` 与产物一起上传即可。

1. **`lingai.net/fund01/latest.json`**（自有源，可选）—— 备份期间返回 404，
   按 updater 源码行为（`updater.rs:508-512`，`Ok(res)` + `!is_success()` 仅 log 不中断）
   会**自动退到下一条**，不阻断更新检查
2. **`gh-proxy.com/https://github.com/.../releases/latest/download/latest.json`**（兜底）
3. **`github.com/lingyired/fund01/releases/latest/download/latest.json`**（直连）

**端点用 `latest` 但资产 URL 用固定 tag**，两者各司其职：

- 端点跟随 `latest` → 用户始终拿到当前最新清单
- 清单内 `platforms[].url` 用 `releases/download/v<ver>/<file>` →
  lingai.net 长期驻留的老清单不会因新 Release 发布而漂移指向别的版本资产

#### 必做修正 1：显式设置 timeout

`UpdaterBuilder::default()` 的 `timeout: None`（第 176 行），第 458 行 `if let Some(timeout)` 不成立 → **默认不设超时**。

被墙时若 TCP 呈「连上但不响应」黑洞状态，请求会无限期挂起，UI 卡在「检查中」。**必须显式传 `timeout(Duration::from_secs(10))`**，沿用现有 `update.rs` 的 10 秒口径。

#### 必做修正 2：下载阶段无 fallback

`download()`（第 682-687 行）只请求 `self.download_url` 这**一个** URL：

```rust
let response = request.build()?.get(self.download_url.clone())
    .headers(headers).send().await?;   // 失败直接 Err，无重试无备用源
```

**endpoint 数组只管拉清单，不管下载包。** 清单里的 `platforms[].url` 指向 GitHub 就还是 GitHub。

→ 当前选择：**清单与产物都挂 GitHub Release**（不自建）。若日后国内直连 GitHub 确实慢/断，
再改为「清单托管 lingai.net + 服务端把资产 URL 改写成镜像地址」：

```
GitHub 原始:  https://github.com/.../releases/download/v1.7.0/Fund01_x64-setup.exe
返回客户端:    https://gh-proxy.com/https://github.com/.../Fund01_x64-setup.exe
```

**签名不受影响** —— `.sig` 是对文件内容计算的，换域名不改字节，验签照样通过。

> 注：客户端「手动下载」兜底按钮直接用清单里的 `download_url`，
> 因此该 URL 即便被墙，用户也有浏览器可用的独立路径。

#### 已知局限

- 若代理源返回 200 但是错误页 HTML → 触发「200 + JSON 解析失败 → 不 fallback」，整个检查直接报错。所以代理源质量是关键变量，自有源放第一位很重要。
- `no_proxy` 选项（2.10 新增，第 461 行）：**reqwest 默认走系统代理**。若本机代理规则把 `lingai.net` 也劫持进内网，更新检查会失败——这也是必须设 timeout 的另一理由。

## 5. 代码改动清单

### 5.1 Rust 侧

| 文件 | 改动 |

| `update.rs` | **重写**。移除 `http::http_get_json` + 手写版本比较，改为 `app.updater()?.check()`；**必须显式传 `timeout(Duration::from_secs(10))`**，默认无超时会被黑洞连接挂死 |
| `commands.rs` | `check_update` 语义调整；新增 `install_update`（下载+安装+可选重启） |
| `capabilities/default.json` | 新增 `"updater:default"`、`"process:default"` |

**关键设计决策：`update.rs` 怎么改？**

现有 `CheckUpdateResult { latestVersion, homepage, downloadUrl }` 是给「打开浏览器」设计的。应用内安装后语义完全变了。方案：

- **保留** `check_update` 命令名和返回结构中的 `latestVersion`（前端 banner 文案「发现新版本 vX.Y.Z」可零改动）
- **新增** `notes`（更新说明）和 `install_update`
- `downloadUrl` 语义从「浏览器下载」变为「fallback 手动下载链接」（GitHub Release 页），保留降级路径 —— 万一自动安装失败，用户还能手动

> **保留手动降级路径是硬要求**：updater 在某些环境（macOS 权限、非公证包、Windows 被杀软拦）会安装失败，没有手动兜底就成了死路。

## 6. 阶段划分

### 阶段 1 · Windows 自动更新（无外部依赖，可立即验证）

1. 加 `tauri-plugin-updater` + `process` 依赖，注册插件与权限
2. `tauri.conf.json`：加 `bundle.createUpdaterArtifacts: true` + `plugins.updater.pubkey/endpoints/windows.installMode`
3. 生成 updater 签名密钥对（公钥进 conf，私钥进 GitHub Secret）
4. `update.rs` 重写 + 前端改造
5. CI Windows job 产出 `.sig` + `latest.json`，上传 artifact
6. 本地验证：装旧版 → 发新版 → 应用内更新成功

**验收**：Windows x64 用户能一键更新成功；安装包被篡改时拒绝安装。

### 阶段 2 · macOS Developer ID 签名 + 公证迁移

1. 申请 Developer ID Application 证书 + App Store Connect API Key
2. 替换 GitHub Secrets；`tauri.conf.json` 的 `signingIdentity` 改 Developer ID
3. CI 加公证 + stapling 步骤
4. 验证：装公证后的 dmg，**不再需要** `xattr -rd com.apple.quarantine`

**验收**：新装的 Fund01.app 双击直接打开，无「已损坏」弹窗。

### 阶段 3 · macOS 自动更新 + 镜像源

1. macOS job 产出 `.app.tar.gz` + `.sig`，并入 `latest.json`
2. `lingai.net` 部署清单托管（可选，作为首选 endpoint）
3. 灰度：先自己机器验证端到端，再发 Release

## 7. 已知边界与风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **私钥丢失** | 无法给已安装用户发更新 | 私钥必须离线备份 + 存密码管理器；**这是不可逆的单点** |
| Windows arm64 是 `experimental` | 构建可能失败 | 清单动态生成，失败的平台不写入（否则拖垮所有用户的更新检查） |
| GitHub 在国内 200 但慢/内容异常 | 200+坏 JSON 不 fallback（`res.json().await?` 硬跳出）；慢则默认无超时挂死 | 清单托管到 `lingai.net` 作首选 + **显式设 10s timeout** + 服务端改写 URL 为镜像地址 |
| **下载阶段无 fallback** | 包只请求清单给的单个 URL | 服务端在清单里直接下发镜像 URL（签名按内容算，换域名不影响） |
| reqwest 默认走系统代理 | 本机代理规则若劫持 `lingai.net` → 检查失败 | 自有源优先 + 必要时用 2.10 的 `no_proxy` |
| macOS 未公证的包 updater 会失败 | mac 端更新体验差 | 阶段 2 先解决公证，再开 mac 自动更新 |
| 替换 `/Applications` 需权限 | 非 admin 安装的用户失败 | 手动降级路径（打开 Release 页） |
| **老用户没有 updater** | 已安装的 1.6.x 无法被新版本自动更新 | **不可解**。1.7.0 的更新提示只能靠现有 `version.json` 通道触达老用户，他们需手动装 1.7.0，之后才有自动更新 |
| portable Windows 版 | 无法自动更新 | 该构建不注册 updater 插件，前端降级为「手动下载」 |

> ⚠️ **「老用户死区」必须提前认知**：自动更新只对装了带 updater 的版本的用户生效。现有 1.6.x 用户仍走 `version.json` 提示 + 浏览器下载，直到手动装上 1.7.0。所以 **`version.json` 通道要保留至少一个版本周期**。
