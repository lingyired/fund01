# 导入后「持有成本」显示 `-` 的诊断报告

> 状态：**已修复（2026-08-08，commit a3d749d，chrome v1.2.44）**。修复方案见 §5.1 落地：设置页所有写持仓入口（导入/添加/编辑保存/分组删除重命名）成功后统一 `refreshHoldingsCache`（chrome 清 cache-* + `refreshAll(true)` 强制重算，跳过非交易时段过滤）。
> 触发场景：用户按统一录入 spec 改完代码后，批量导入一份 JSON（13 只基金，含 `amount` + `holdProfit`），导入成功但 popup 持仓列表「持有成本」列显示 `-`。
> 诊断日期：2026-08-08（周六，非交易时段）

---

## 1. 现象

导入成功后：

- popup 持仓列表（读 SW 缓存）的「持有成本」列显示 `-`；
- 导入的 JSON 中 12 只基金均带了 `amount`（>0）与 `holdProfit`（有限值），只有 `028375`（amount=0，无 holdProfit）本就不应有成本。

用户直觉猜测："是不是我改代码把成本弄丢了？"

---

## 2. 一句话根因

**成本其实已经正确写进 config 了，问题出在 popup 读的是过期的 SW 缓存（`cache-holdings`），导入持仓不会触发 SW 重算缓存，叠加当前是周六（非交易时段 alarm 刷新被跳过），缓存一直停在上一次计算快照。**

这不是录入/存储回归，是"写 config 后未强制刷新展示缓存"的展示层 bug，与之前「添加/编辑后弹层不刷新」同源。

---

## 3. 证据链（逐层走查）

### 3.1 显示层：`holdingCostOf` 在 `cumPnl == null` 时返回 `-`

`packages/core/src/holdingsCalc.ts:24`

```ts
export function holdingCostOf(amount, cumPnl) {
  if (amount == null || !Number.isFinite(amount)) return null
  if (cumPnl == null || !Number.isFinite(cumPnl)) return null   // ← 持有收益为 null → 上层渲染 '--'
  ...
}
```

注释（`:22`）明写：`null 表示未录入成本（持有收益为 null），UI 渲染 --`。

### 3.2 计算层：`cumPnl`（持有收益）为 null 的唯一条件是 `costs` 无效

`packages/core/src/holdingsCalc.ts:114-229`

```ts
let totalCostRow = 0
const hasCost = fund.costs && Object.values(fund.costs).some((c) => c > 0)  // 有有效成本单价
...
totalCumPnl: hasCost ? round2(liveAmount - totalCostRow) : null,            // ← 无成本 → null
```

即：**`fund.costs` 里该分组没有 `>0` 的成本单价 → 持有收益 = null → 持有成本显示 `-`**。

### 3.3 数据层：导入已经正确反推并写入 `costs`

导入循环调用 `createFund`（`OptionsApp.tsx:1619-1633`，确实把 `holdProfit` 传入）。

`createFund` 的成本反推逻辑（`packages/ui/src/lib/fundOps.ts:347-357`）：

```ts
// 成本单价优先级：显式 cost > holdProfit 反推 > 保留 prev
if (payload.cost != null && payload.cost > 0) {
  costs = {...prevCosts, [group]: Number(payload.cost) || 0}
} else if (holdProfit != null && Number.isFinite(holdProfit) && shares > 0) {
  const totalCost = amount - Number(holdProfit)   // 总成本 = 市值 - 持有收益
  const price = Math.round((totalCost / shares) * 1e6) / 1e6
  if (price > 0) costs = {...prevCosts, [group]: price}
}
```

对本次导入的 12 只正金额基金逐一复核：`totalCost = amount - holdProfit` 均为正（含负 `holdProfit` 的项 totalCost 反而更大），`shares > 0`（由 amount÷净值折算），故 `price > 0` 必然成立 → **`costs` 一定写进 config**。

> `028375`（amount=0）无 `holdProfit`，`shares` 折算为 0，`price` 分支不进入，本就无成本 → 显示 `-` 是**正确的**。

**结论：数据层（config）成本数据是对的。**

### 3.4 展示层真相：popup 读 SW 的 `cache-holdings`，导入不触发其刷新

- popup 持仓列表不实时读 config，而是读 SW 算好后写进 `chrome.storage.local` 的 `cache-holdings`（`packages/ui/src/hooks.ts:26` → `ports.data.fetchHoldings()`）。
- SW 监听 config 变化后，**仅在切换数据源（quoteSource）时才 `refreshAll`**（`apps/chrome/src/background/index.ts:433-436`）：

```ts
if (oldSource !== newSource) {
  chrome.storage.local.remove(CACHE_KEYS)
    .then(() => refreshAll(true))   // 只有切换数据源才重算
}
```

导入持仓**不改变数据源** → SW 不重算 → `cache-holdings` 仍是导入前的旧快照（那些基金当时还没有 `costs`）→ 持有收益算不出 → 持有成本显示 `-`。

### 3.5 周六叠加：定时 alarm 刷新也被跳过

SW 的定时刷新（`apps/chrome/src/background/index.ts:154` `refreshAll(force=false, kind)`）在非交易时段直接 return（`:225-226`）：

```ts
if (tasks.length === 0) {
  return // 所有数据源都在非交易时段，跳过
}
```

当前是周六，alarm 触发的 `refreshAll(false)` 走到这里被跳过。**于是 `cache-holdings` 在周末不会被任何自动路径更新**，缓存残留贯穿整个周末。

## 4. 30 秒自证（区分"costs 没写" vs "缓存残留"）

打开 **设置页 → 编辑持仓** 表格，看「持有成本」列（该表读 config **实时算**，不走 SW 缓存）：

- 若编辑页**有值（¥xxxx）**，而 popup 列表是 `-` → 100% 确认是**缓存残留**（成本其实写进去了）。符合本例预期。
- 若编辑页**也是 `-`** → 那才是 `costs` 真没写，需回查导入/折算逻辑（本例几乎不可能）。

---

## 5. 修复方向（已实施，2026-08-08）

### 5.1 触发点
导入全部完成后，主动给 SW 发一条清除缓存 + 强制刷新消息，让它重算并写回 `cache-holdings`。

- 已有现成入口 `ports.data.clearCache()`：`OptionsApp.tsx:2090`、`:2112`（"重置全部数据""清除缓存"按钮已用它），直接复用即可。
- 调用位置：导入循环 `await Promise.all(rows.map(e => createFund(...)))` 之后（约 `OptionsApp.tsx:1617` 所在函数末尾）。
- **实施（v1.2.44）**：新增 `fundOps.ts::refreshHoldingsCache(ports)` 统一 helper（chrome：`clearCache`；tauri：回退 `triggerRefresh`；失败静默），并在**全部设置页写持仓入口**成功后调用：导入 `runImport`、添加 `AddFundSection.onSubmit`、编辑保存 `EditHoldingsSection.handleSave`、删除分组 `deleteGroup`、分组重命名/删除 `handleRenameGroup`/`handleRemoveGroup`。popup 内弹层本就走 `triggerRefresh`（SW `REFRESH` = force=true），无需改。

### 5.2 为什么周六也能修好

`refreshAll(true)` 的 `force=true` 会**跳过非交易时段过滤**（`apps/chrome/src/background/index.ts:154` 参数定义 + 内部 `force` 分支），所以强制刷新不受周末影响，能立即重算缓存。

### 5.3 影响范围

- 这是展示层问题；数据层（config 的 `costs`/`allocations`）始终正确。
- 即使不修，等**周一交易时段** alarm 正常刷新后，`-` 也会自动变正确——只是周末体验差。
