# tauri-plugin-multiline-menubar 右键菜单退出挂起 —— 修改方案

> 提供给插件维护者的问题报告与修复建议（v1.6.1 提案）
> 日期：2026-08-17
> 关联仓库：github.com/lingyired/tauri-plugin-multiline-menubar（当前 tag v1.6.0）

---

## 一、问题现象（宿主 app 实测）

macOS 上右键点击菜单栏状态项 → 弹出右键菜单 → 点击「退出」类菜单项（插件保留 id `quit`/`quit2`，宿主经 `on_menu_event` 同步调用 `app.exit(0)`）后：

1. **app 长时间不退出**（实测等待数分钟无动静）；
2. **进程 100% CPU**；
3. **内存持续增长**；
4. **手动点击一下 menubar 后 app 才退出**。

宿主侧已通过日志 + `sample` 采样双证定位（见第三节），确认根因在插件的**右键菜单弹出方式**与 **NSStatusBarButton 自身 tracking loop** 的冲突，而非宿主退出逻辑本身。

---

## 二、涉及代码路径

### 1. 右键菜单弹出（native，`src/native/multiline_menubar.mm`）

`handleClick:` 中右键分支：

```objc
- (void)handleClick:(NSEvent *)event {
    // ... 左键/右键判定，g_clickCallback 上报 ...
    if (isRight && inst.menu != nil) {
        NSPoint location = [button isFlipped] ? NSMakePoint(0, NSMaxY(bounds) + 4)
                                              : NSMakePoint(0, NSMinY(bounds) - 4);
        [button highlight:YES];
        [inst.menu popUpMenuPositioningItem:nil atLocation:location inView:button]; // ← modal tracking loop
        [button highlight:NO];
    }
}
```

`popUpMenuPositioningItem:` 会运行一个 **modal tracking loop**（`NSEventTrackingRunLoopMode`），同步阻塞直到菜单关闭。

### 2. 退出处理（Rust，`src/desktop.rs`）

`init()` 注册的全局菜单事件中：

```rust
app.on_menu_event(|app, event| {
    let item_id = event.id().0.as_str();
    // ...
    if QUIT_ITEM_IDS.contains(&item_id) {   // ["quit", "quit2"]
        app.exit(0);                          // ← 在菜单 action（tracking loop 内）同步退出
        return;
    }
    // ...
});
```

## 三、根因分析（sample 实证）

### 3.1 采样证据

退出挂起期间 `sample` 主线程栈（关键帧）：

```
-[NSApplication run]
  -[NSApplication _handleEvent:] → sendEvent:
    -[NSStatusBarWindow sendEvent:] → _routeRightMouseDownEvent
      -[NSStatusBarButton rightMouseDown:]
        -[NSStatusBarButtonCell trackMouse:inRect:ofView:untilMouseUp:]   ← button 自身 tracking
          NSControlTrackMouse
            -[NSDragEventTracker trackEvent:usingHandler:]
              -[NSWindow trackEventsMatchingMask:timeout:mode:handler:]
                -[NSApplication nextEventMatchingMask:untilDate:inMode:dequeue:]  ← NSEventTrackingRunLoopMode
                  _DPSBlockUntilNextEventMatchingListInMode
                    ReceiveNextEventCommon
                      AcquireEventFromQueue ×2192（事件队列持续有事件 → 忙转）
                        __CFRunLoopDoObservers
                          (fund01-tauri observer 回调)
                            -[NSEvent _postAtStart:]（反复向事件队列 post 事件）
```

### 3.2 机制还原

1. **右键点击** NSStatusBarButton → `rightMouseDown:` → 进入 `trackMouse:untilMouseUp:`（button 自身的 tracking loop，等待 `rightMouseUp` 结束）；
2. `handleClick:` 里 `popUpMenuPositioningItem:` 弹出菜单 —— **modal loop 消费掉了本次点击的 `rightMouseUp`**；
3. 菜单关闭、`popUpMenuPositioningItem:` 返回后，**外层 `trackMouse:` 仍在等待一个永远不来的 `rightMouseUp`** → tracking loop 卡死在 `NSEventTrackingRunLoopMode`（菜单已关，tracking 未死）；
4. 此时宿主 `app.exit(0)`（tauri）→ `ControlFlow::Exit` → tao 的 `cleared()`（`BeforeWaiting` observer）**每轮重复执行** `[NSApp stop:]` + `post_dummy_event`（向 NSEvent 队列 post 一个 ApplicationDefined 事件）；
5. 事件队列因此**持续非空** → 卡死的 `trackMouse` 的 `nextEventMatchingMask` **永不阻塞** → 每轮取走 dummy 后继续等 → 无限忙转：
   - **100% CPU**（`AcquireEventFromQueue` 高频命中）；
   - **内存持续增长**（dummy 事件在队列中持续堆积）；
6. `[NSApp stop:]` 只能结束**外层** `[NSApp run]` 循环，**无法结束卡死的内层 `trackMouse` tracking loop** → 退出挂起；
7. **手动点击 menubar** → 产生真实的 mouseDown/mouseUp 事件流 → `trackMouse` 等到 mouseUp → tracking 结束 → 外层 `[NSApp run]` 检查到 stop → 退出。

### 3.3 结论

> **根因 = 在 NSStatusBarButton 自身的 `trackMouse:` tracking 期间，用 `popUpMenuPositioningItem:` 弹出 modal 菜单，导致 `rightMouseUp` 被 modal loop 消费、外层 tracking 永久卡死；任何依赖 `[NSApp stop:]`/`app.exit` 的退出在 tracking 未结束时都会挂起。**

## 四、修改方案（两个改动，缺一不可）

### 改动 A：native 层 —— 菜单关闭后补发 `rightMouseUp`，让 button tracking 正常收尾

文件：`src/native/multiline_menubar.mm`，`handleClick:` 右键分支。

```objc
- (void)handleClick:(NSEvent *)event {
    // ... 左键/右键判定，g_clickCallback 上报 ...
    if (isRight && inst.menu != nil) {
        NSPoint location = [button isFlipped] ? NSMakePoint(0, NSMaxY(bounds) + 4)
                                              : NSMakePoint(0, NSMinY(bounds) - 4);
        [button highlight:YES];
        [inst.menu popUpMenuPositioningItem:nil atLocation:location inView:button];
        [button highlight:NO];

        // ── 新增：补发 rightMouseUp ──────────────────────────────────────────
        // popUpMenuPositioningItem: 的 modal loop 消费掉了本次点击的 rightMouseUp，
        // 导致 button 外层 trackMouse:untilMouseUp: 永远等不到 mouseUp、卡死在
        // NSEventTrackingRunLoopMode（菜单关了 tracking 还活着）。补发一个
        // rightMouseUp 让外层 tracking 正常收尾，run loop 回到 default mode。
        NSEvent *cur = [NSApp currentEvent];
        NSEvent *mouseUp = [NSEvent mouseEventWithType:NSEventTypeRightMouseUp
                                              location:[button convertPoint:NSZeroPoint toView:nil]
                                         modifierFlags:0
                                             timestamp:cur.timestamp
                                          windowNumber:cur.windowNumber
                                               context:nil
                                           eventNumber:0
                                            clickCount:1
                                              pressure:0];
        [NSApp postEvent:mouseUp atStart:NO];
        // ─────────────────────────────────────────────────────────────────────
    }
}
```

> 说明：
> - `location` 参数不影响 tracking 结束判定（trackMouse 只关心事件类型与窗口），但建议用 button 的实际屏幕位置；
> - 若担心 `postEvent:` 时序，可改为 `dispatch_after` 到主队列再 post，但**必须在 popUpMenuPositioningItem 返回后**、trackMouse 仍存活时投递。

### 改动 B：Rust 层 —— 退出改为延迟 dispatch，不再在菜单 action 内同步退出

文件：`src/desktop.rs`，`init()` 的 `on_menu_event` 闭包。

```rust
if QUIT_ITEM_IDS.contains(&item_id) {
    // macOS：on_menu_event 在菜单 action（modal tracking loop）内同步回调。
    // 即便改动 A 补发了 rightMouseUp，此刻 popUpMenuPositioningItem 尚未返回、
    // trackMouse 尚未收尾，同步 app.exit(0) 的 [NSApp stop:] 仍可能与 tracking
    // 竞争。延迟 ~200ms，等菜单 dismiss + tracking 收尾完成、run loop 回到
    // default mode 后，再在主 run loop 里干净退出。
    let app = app.clone();
    tauri::async_runtime::spawn(async move {
        tokio::time::sleep(std::time::Duration::from_millis(200)).await;
        app.exit(0);
    });
    return;
}
```

> 说明：
> - 延迟时长取 200ms：菜单 dismiss 动画 + trackMouse 收尾在 200ms 内必然完成，宿主感知无延迟；
> - `tauri::async_runtime::spawn` 在 tokio 线程执行，`app.exit(0)` 经 tao proxy 跨线程投递，安全；
> - 若不引入 tokio 依赖（插件可能无 tokio），可退化为 `std::thread::spawn` + `std::thread::sleep`，语义相同。

## 五、验证清单（发布前必须过）

用插件自带 demo（`examples/demo`）验证：

| # | 场景 | 预期 |
|---|------|------|
| 1 | 右键状态项 → 点「退出」菜单项 | app 立即退出，无 100% CPU、无内存增长 |
| 2 | 右键状态项 → 点其他菜单项（如打开窗口） | 菜单正常关闭，窗口正常打开，trackMouse 不卡 |
| 3 | 右键 → 按 Esc 关闭菜单 | 菜单关闭后 trackMouse 收尾，后续交互正常 |
| 4 | 右键 → 点击菜单外关闭 | 同上 |
| 5 | 多实例（≥2 个状态项）反复右键退出 | 每个实例退出均干净 |
| 6 | 退出前用 `sample <pid> 3` 抓栈 | 主线程不应卡在 `trackMouse:` / `NSControlTrackMouse` |

回归项：左键点击弹 popup、hover 事件、⌘-拖出 remove 事件，均不应受影响。

## 七、宿主（fund01）现状与配合

- fund01 当前已用应用层 workaround 绕开该问题：退出菜单项改用自定义 id `quit-fund01`（绕过插件 `QUIT_ITEM_IDS` 的同步 exit），并在宿主侧用 `std::process::exit(0)` 直接终止（不依赖 `[NSApp stop:]`），**已实测秒退**；
- 插件 v1.6.1 发布后，fund01 **可改回**标准 `quit` id + `app.exit(0)`（更优雅、走 tauri 正常退出清理），但**非必须**；在插件修复未验证前，fund01 保持现有兜底不动；
- 若插件修复后仍有边缘场景挂起，fund01 的 `process::exit` 兜底始终有效，两者不冲突。
